# Private Individual Customer Support — Design Spec

**Date:** 2026-04-22
**Status:** Draft — awaiting user approval
**Author:** Claude (MERT-M agent)

## 1. Контекст и мотивация

MERT-M разпространява професионално кухненско оборудване предимно на B2B
клиенти (ресторанти, хотели, обекти с фирми), но понякога **случайни клиенти
без фирма** (частни лица) купуват стока на място в склада (напр. готвач
купува домакински шкаф Liebherr). В момента системата изисква партньорът
да има ЕИК и е ориентирана само към юридически лица, което блокира тези
продажби.

### Защо без ЕГН?

В България **не е практика** търговец да изисква ЕГН на физическо лице
при обикновена касова продажба. Клиентите почти никога не дават ЕГН-то
си и няма законово задължение за това — фискалната бележка и фактурата
към физическо лице могат да се издадат без ЕГН. Затова ЕГН **няма да
се въвежда изобщо** в системата — нито задължително, нито по избор.

### Какво остава задължително по закон

- **Фискална бележка от касов апарат** — винаги, при плащане в брой.
  Издава се от фискалното устройство, а не от нашия софтуер. Нашата
  система регистрира **факта** на касовата продажба (разписка за плащане
  в брой), но физическата бележка идва от отделно устройство.
- **Фактура (по желание на клиента)** — може да се издаде на физическо
  лице със само име и адрес (или дори без тях, като „Физическо лице —
  краен потребител").

## 2. Цел

Позволи продажба и фактуриране на физически лица (частни клиенти без
фирма) без промяна на DB схемата и без въвеждане на ЕГН. Работата с
B2B партньори остава непроменена.

## 3. Обхват (scope)

**В обхвата:**

- Типизиране на партньорите: `legal_entity` (юридическо) vs `individual` (физическо).
- UI за създаване на физическо лице без ЕИК/ДДС номер.
- Един „специален" партньор — **„Физическо лице — краен потребител"** —
  за анонимни касови продажби, където клиентът не иска да се именува.
- Издаване на фактура към физическо лице (без ЕИК ред в PDF-а).
- Показване на типа партньор в списъка и фактурите.

**Извън обхвата:**

- ЕГН поле или валидация.
- Промяна на фискалните устройства / касови апарати.
- НАП-интеграция за автоматично фискализиране (остава ръчно на касата).
- Промяна на логиката за Еконт поръчки (индивидуалните клиенти обикновено
  пазаруват на място в склада, не с куриер — ако трябва куриер, те вече
  могат да се въведат като физическо лице и процесът продължава нормално).

## 4. Архитектура

### 4.1 Data model (без промени в schema)

Таблицата `partners` **вече съдържа** всичко необходимо:

| Поле           | Тип                            | За legal_entity               | За individual                                         |
| -------------- | ------------------------------ | ----------------------------- | ----------------------------------------------------- |
| `name`         | varchar(255) NOT NULL          | Търговско име                 | Име на лицето или „Физическо лице — краен потребител" |
| `print_name`   | varchar(255)                   | Име за печат                  | = `name`                                              |
| `eik`          | varchar(20) nullable           | Задължително (9 или 13 цифри) | **Винаги NULL**                                       |
| `vat_number`   | varchar(20) nullable           | По избор                      | **Винаги NULL**                                       |
| `address`      | text nullable                  | По избор                      | По избор                                              |
| `city`         | varchar(255) nullable          | По избор                      | По избор                                              |
| `phone`        | varchar(50) nullable           | По избор                      | По избор                                              |
| `email`        | varchar(255) nullable          | По избор                      | По избор                                              |
| `partner_type` | varchar(20) default 'customer' | `legal_entity`                | `individual`                                          |

**Важно:** `partner_type` в момента съдържа `'customer'` / `'supplier'`
(бизнес роля). Ще добавим нов ред — вид субект. За да не разрушим
съществуващия смисъл, ще го **разширим** с още две стойности:

- Запазени: `customer` (приема се като „legal_entity customer" по
  подразбиране, за съвместимост с вече въведени партньори), `supplier`.
- Нови: `individual` (физическо лице, краен потребител).

Алтернативно бихме могли да въведем отделна колона `entity_type`
(`legal_entity` / `individual`), но предпочитаме минимална schema промяна.
За физическо лице задаваме `partner_type = 'individual'` директно.

### 4.2 Seed data — общ анонимен партньор

При startup migration се създава (idempotent) един партньор:

```
name          = 'Физическо лице — краен потребител'
print_name    = 'Физическо лице — краен потребител'
partner_type  = 'individual'
eik           = NULL
vat_number    = NULL
```

Използва се, когато продавачът не записва име на клиента (най-често
при случайни касови продажби). В UI този партньор се показва с различна
иконка и надпис „(анонимен краен потребител)".

### 4.3 Invoicing flow

Нищо ново по същество — фактурата вече не рендерира ЕИК ред, ако липсва
(`invoice-pdf.ts` използва `...(party.eik ? [...] : [])`). Единствената
разлика: ако партньорът е `individual`, PDF-ът показва **„Клиент
(физическо лице):"** вместо „Клиент:" и без ДДС номер ред.

Задължителните стъпки при продажба на физическо лице:

1. Пазачът/търговецът или избира съществуващо физическо лице, или
   създава ново, или избира „Физическо лице — краен потребител".
2. Прави поръчка както обикновено.
3. Издава касова бележка **от фискалното устройство** (извън софтуера).
4. Създава разписка за плащане в брой (или банков превод) в системата.
5. По желание — издава фактура с `Partner = individual`.

## 5. UI промени

### 5.1 Създаване/редакция на партньор (`Partners.tsx`)

Добавя се **радио бутон / сегмент** в началото на формата:

```
Тип клиент:   ○ Юридическо лице     ○ Физическо лице
```

Визуална логика:

| Поле            | Юридическо          | Физическо                  |
| --------------- | ------------------- | -------------------------- |
| Име             | Задължително        | Задължително (или default) |
| ЕИК             | Задължително (9/13) | **Скрито**                 |
| ДДС номер       | По избор            | **Скрито**                 |
| Адрес           | По избор            | По избор                   |
| Град            | По избор            | По избор                   |
| Телефон/email   | По избор            | По избор                   |
| Банкови детайли | По избор            | **Скрити**                 |

Валидация:

- `legal_entity`: ЕИК валидация `/^\d{9}$|^\d{13}$/` остава.
- `individual`: `name` задължително, всичко останало по избор, никаква
  ЕИК проверка, никакъв lookup в НАП.

При запазване: `partner_type` се сетва на `legal_entity` или `individual`
според радио бутона (не остава `customer`).

### 5.2 Списък партньори

Добавя се филтър „Тип: Всички / Юридически / Физически" и нова колона
**Тип** с иконка (🏢 или 👤). ЕИК колоната остава, показва „—" за
физическите лица.

### 5.3 Създаване на поръчка (`Orders.tsx`) — **главен flow**

Реалността в ТехноМаркет / Практикер / Метро: касиерът **не пита** за
име или телефон при обикновена продажба на частно лице. Клиентът
показва стока, плаща, получава касова бележка — край. Точно това
поведение копираме.

Формата за нова поръчка започва със сегмент-бутон (2 опции):

```
┌────────────────────────────┬────────────────────────────┐
│   🏢  Фирма (с ЕИК)        │   👤  Физическо лице        │
└────────────────────────────┴────────────────────────────┘
```

#### Режим „Фирма (с ЕИК)"

Текущото поведение остава непроменено:

- Dropdown с търсене в съществуващите `legal_entity` партньори.
- Ако клиентът не съществува → бутон „Нов партньор" отваря Partners
  modal (както сега).

#### Режим „Физическо лице" — **БЕЗ въпроси за данни**

Един клик, нищо повече. Системата автоматично избира seed партньора
„Физическо лице — краен потребител" и отива направо към добавяне на
артикули. Няма имена, няма телефони, няма адреси.

**Цялата формация на поръчка е идентична** със съществуващата — единствената
разлика е че `partner_id` e на seed-анонимния партньор вместо на фирма.

Касовата бележка излиза от фискалния касов апарат (както винаги). Нашата
система записва плащането като разписка в брой и това е достатъчно.

#### API промяна (backend)

`POST /orders` приема минимален `customer_type` flag:

```ts
{
  partner_id: number,            // За фирма: ID на партньора
                                 // За физ. лице: ID на seed анонимния партньор
  customer_type: 'legal' | 'individual',
  items: [...],
  // ... съществуващите полета
}
```

Backend logic:

- `customer_type === 'legal'` → изисква `partner_id` на `legal_entity`.
- `customer_type === 'individual'` → изисква `partner_id` да сочи към
  партньор с `partner_type='individual'` (по default това е seed-анонимният).

Реално в UI-а при „Физическо лице" frontend-ът автоматично попълва
`partner_id = <seed anonymous id>` и никога не пита за нищо.

#### Какво ако клиентът поиска фактура на конкретно име?

Това се случва рядко (за гаранция се използва касовата бележка с
печат от магазина). Ако все пак поиска:

- Бутонът „Издай фактура" отваря диалог.
- За `individual` поръчки диалогът има **по избор** поле „Име на клиента
  (ако клиентът иска да е на име)".
- Ако се попълни → PDF-ът показва „Клиент: [име]" вместо „Клиент:
  Физическо лице — краен потребител".
- Името НЕ се записва в `partners` — просто се включва в PDF-а и в
  invoice record-а (колона `client_display_name` nullable). Няма
  натрупване на партньори за еднократни продажби.

Адрес, телефон, и други „лични данни" **не се питат въобще** — не
са нужни за валидна фактура към физ. лице в България.

#### UI дизайн детайли

- Сегмент-бутонът е **sticky на върха** на формата — може да се смени
  и по средата на попълването (със confirm dialog ако има попълнени данни).
- Иконките 🏢 / 👤 се използват последователно в целия UI (списъци,
  detail views, фактури) за визуално разграничаване.

### 5.4 DB промяна за опционално име на фактура към физ. лице

Единствената schema промяна е:

```sql
ALTER TABLE invoices
  ADD COLUMN client_display_name varchar(255);
```

Nullable. Използва се само когато клиент-физ.лице изрично поиска
фактура на конкретно име. В PDF-а го показваме приоритетно пред
`partner.name`, ако е попълнено.

### 5.5 Издаване на фактура

Няма промяна в UI — бутонът „Издай фактура" работи и за физически лица.
Backend-ът не изисква ЕИК. Ако партньорът е `individual`, PDF-ът:

- Премахва реда „ЕИК:".
- Премахва реда „ДДС номер:" (вече е условно).
- Показва надпис „**Клиент (физическо лице):**" вместо „Клиент:".
- Всичко останало (стоки, суми, ДДС 20%, обща сума) е непроменено.

## 6. Backend промени

### 6.1 Миграция (idempotent)

```sql
-- 2026-04-22-individual-partner-type.sql
-- Insert the anonymous individual partner if missing.
INSERT INTO partners (name, print_name, partner_type)
SELECT 'Физическо лице — краен потребител',
       'Физическо лице — краен потребител',
       'individual'
WHERE NOT EXISTS (
  SELECT 1 FROM partners
  WHERE name = 'Физическо лице — краен потребител'
    AND partner_type = 'individual'
);
```

Не се добавят нови колони, не се променя съществуваща структура.

### 6.2 API валидация (`routes/partners.ts`)

В `POST /partners` и `PUT /partners/:id` валидационният Zod schema
(или ръчна проверка) се разделя по `partner_type`:

```ts
if (body.partner_type === "individual") {
  // name required, everything else optional, no EIK check
} else {
  // legal_entity: name + eik (9 or 13 digits) required
}
```

### 6.3 Invoice PDF (`invoice-pdf.ts`)

Добавя се условие в `renderPartyBlock`:

```ts
const label =
  party.partner_type === "individual" ? "Клиент (физическо лице):" : "Клиент:";
```

Редовете за ЕИК/ДДС остават вече-условно-рендерирани.

## 7. Тестване

### 7.1 Ръчни сценарии (smoke)

1. Създай нов партньор от тип „Физическо лице" само с име „Иван Петров"
   → запазва се, не пита за ЕИК.
2. Създай поръчка към този клиент → проходи нормално, излиза в списъка.
3. Създай разписка за плащане в брой → сумата излиза в отчета.
4. Издай фактура → PDF показва „Клиент (физическо лице): Иван Петров",
   няма ред за ЕИК.
5. Избери „Физическо лице — краен потребител" (анонимния) → всичко работи
   без попълване на никакви данни освен сумата.
6. Опитай да създадеш Юридическо лице без ЕИК → валидацията блокира.

### 7.2 Автоматизирани тестове

- `partners.test.ts`: тест че `individual` партньор без ЕИК се приема,
  тест че `legal_entity` без ЕИК се отхвърля.
- `invoice-pdf.test.ts`: тест че фактура за `individual` не съдържа
  „ЕИК:" в резултатния PDF.

## 8. Рискове

- **Съществуващи данни**: всички текущи партньори имат `partner_type`
  от вида „customer"/„supplier" (бизнес роля, не вид субект). Трябва да
  ги третираме като legal_entity по подразбиране — UI и PDF не правят
  explicit проверка, само показват ЕИК ако има такъв. Миграция за
  backfill **не е необходима** — излишно сложно и рисковано.
- **НАП изисквания**: при касова продажба на физ. лице касовата бележка
  винаги е на фискалното устройство, затова софтуерът няма регулаторна
  отговорност за това. Важно е потребителите да разбират, че
  „разписка" в нашата система ≠ „касова бележка".
- **Обърквания в отчетите**: трябва да се уверим, че отчетите (Analytics,
  Payments PDF) работят еднакво за двата типа клиенти. Те групират по
  `partner_id`, не по `partner_type`, така че няма проблем.

## 9. Заключение

Минимална промяна: няма нова DB колона, само един нов seed ред, три малки
промени в UI (radio button, списъчна колона, PDF label) и условна
валидация в partners API. ЕГН не се въвежда никъде. Анонимният партньор
„Физическо лице — краен потребител" покрива случая „клиент не дава данни
изобщо".
